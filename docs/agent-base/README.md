# Bootstrap-контракт агентской задачи

База подготовлена по Adaptive Agent Design Team 0.2.0. Сейчас существует только bootstrap: задача продукта неизвестна, стек не выбран, feature workspace и project agents отсутствуют. Шаблоны не являются согласованными требованиями, рабочим runtime или доказательствами проверок.

## Слои работы

| Слой | Назначение и источник |
| --- | --- |
| `workflow.md` | Полный маршрут 00–15 и фактические состояния; источник истины для переходов |
| `phases/` плагина | Когда выполнять работу, prerequisites, gates и DoD |
| `role-skills/` плагина | Как роль анализирует, проектирует, реализует или проверяет |
| `skils/<feature>-<domain-role>.md` | Кто назначен на конкретный результат; создавать перед реальным dispatch |
| `implementation-plan.md`, `routing.md` | Что выполняется: атомарные задачи, зависимости, владельцы и волны |
| `docs/agent-base/features/<feature>/` | Состояние задачи, решения, handoffs и подтверждающие материалы |

`phases/` и `role-skills/` уже поставляются подключённым плагином и здесь не дублируются. Найдите актуальный `adaptive-agent-design-team/SKILL.md` через каталог навыков; прочитайте entry references и необходимые фазовые/ролевые файлы. Имена фаз плагина 01–06 обозначают группы работ и не заменяют логические checkpoints 00–15.

Инженерные субагенты разрабатывают продукт. Количество разработчиков/проверяющих не определяет число агентов внутри продукта.

## Запуск после получения реальной задачи

1. Примите свободное описание или [форму задачи](templates/task.md). Прочитайте применимые инструкции проекта и соберите факты о коде, среде, тестах, данных и текущих изменениях. Неизвестное сохраняйте как `unknown`; срок и численные бюджеты задаются только по подтверждённым ограничениям.
2. Создайте `features/<feature>/` с первоначальными `requirements.md`, `workflow.md`, `adaptive-plan.md`, `status.md`. Название feature берётся из реальной задачи. В `requirements.md` перенесите задачу; отделите факты, предположения и открытые вопросы.
3. Сравните обычный код, LLM в фиксированном workflow, ограниченный агентский цикл и multi-agent runtime, когда последнее применимо. Выберите минимальную достаточную автономию. Обоснуйте глубину lightweight/standard/high-assurance риском, а не названием задачи. Согласуйте требования на 02.
4. Зафиксируйте уже одобренные технологии. Новые язык/framework/SDK, provider/model/runtime, интеграции и инфраструктуру предложите на 03 до зависимого дизайна и реализации. Известные разрешения не запрашиваются повторно; `not-needed` требует основания.
5. На 04–06 подготовьте дизайн и существенные traces/eval cases, проведите независимое design/security critique, устраните findings или явно зафиксируйте принятие риска. Только затем получите одобрение дизайна.
6. На 07–11 подготовьте план и проверки, проведите независимое plan review. Разложите задачи с одним результатом/владельцем/DoD/check; подготовьте профили и handoffs перед dispatch. Покажите маршрут и права, получите применимое одобрение выполнения.
7. На 12–15 выполняйте готовые задачи, записывайте результаты проверок, проведите независимое final review и получите принятие. План, пример trace и неисполненный eval не считаются доказательствами.

Прямые инструкции пользователя приоритетны. Явное согласование/waiver фиксируется с источником и областью; молчание или общая просьба о базе не заменяют согласование будущей feature. Качество и независимость review нельзя молча исключить.

## Шаблоны и постепенное создание файлов

| Шаблон | Когда и куда переносить |
| --- | --- |
| [task.md](templates/task.md) | На 00–01 в `requirements.md` |
| [workflow.md](templates/workflow.md) | На 00, вести весь маршрут |
| [adaptive-plan.md](templates/adaptive-plan.md) | На 00–01, обновлять при существенных открытиях |
| [status.md](templates/status.md) | На 00, вести текущий шаг и следующий разрешённый переход |
| [decisions.md](templates/decisions.md) | При первом решении/одобрении; сохранять историю |
| [tech-design.md](templates/tech-design.md) | На 04 после требований и применимого stack gate |
| [verification.md](templates/verification.md) | Сценарии на 04, план на 07, фактические результаты на 13 |

`implementation-plan.md`, reviews, `routing.md`, `todos.md` и handoffs создаются на соответствующих этапах по контрактам плагина, а не пустым набором заранее. Для узкой задачи документы можно объединять в разделы с ясными ссылками и владельцами.

При агентском решении существенные контракты обязательны: goal/autonomy/stop (`agent-spec`), tools, trusted state, policies, model contract и failure model. В lightweight они могут быть независимыми разделами `tech-design.md`; в более сложной задаче вынесите в `agent/agent-spec.md`, `tool-catalog.md`, `state-model.md`, `policies.md`, `model-contract.md`, `failure-model.md` и свяжите ссылками. Traces/evals хранят разрешённое/запрещённое поведение и фактический результат отдельно.

RAG, memory, persistent storage, очереди, multi-agent runtime и отдельные approval flows условны: вводятся по доказанной потребности. Для утверждённого deterministic решения агентские разделы — `not-needed` с причиной. Сейчас применимость всех продуктовых решений неизвестна.

## Переходы, восстановление и изменение маршрута

Перед переходом свяжите output, check/review и источник разрешения; обновите workflow/status, покажите текущий и следующий шаг. Не переносите `done` без доказательств или `accepted` без явного принятия. Будущие этапы остаются `proposed`; `waiting-user` применяется к реально достигнутому gate.

При resume прочитайте status/workflow/adaptive-plan/decisions/routing/todos, последние handoffs и соответствующее evidence. Противоречия разрешаются до выполнения. При существенной смене требований, tool semantics, стека, прав или failed review/eval остановите зависимое выполнение, увеличьте revision, сохраните прошлые результаты, укажите затронутые gates и повторите необходимые review/согласования.

## Проверка bootstrap

Для этой документальной подготовки применима проверка существования локальных Markdown-ссылок. Build продукта, runtime-тесты, live-model evals и независимые продуктовые design/plan/final reviews не выполняются: продукт, дизайн и план реализации ещё не заданы. Такой результат не означает готовность будущего агента.
